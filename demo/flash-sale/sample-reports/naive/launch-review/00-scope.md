# Scope
- Product: one-page flash sale for 100 pairs of limited-edition sneakers ($49.99), one pair per customer. The sale opens at midnight, announced by an email blast.
- Users / scale: public consumers. Expected 3,000 visitors within 60 seconds of opening (owner's estimate). Load target derived with a 3× peak factor: ~450 product-page requests/s and ~150 buy requests/s (from `demo/flash-sale/peak-brief.json`: 3 product views + 1 buy per visitor).
- Sensitive data: customer email addresses and shipping addresses (stored in the `orders` table). No card numbers handled by the app.
- Money flows: card payment through an external payment provider, called server-to-server from `POST /api/buy` (`demo/flash-sale/naive/server.mjs:49-57`). Not a hosted checkout: the app decides the amount and triggers the charge itself.
- Auth & roles: passwordless "email login" (`POST /api/login`) is what the owner plans to ship. Roles in code: anonymous, signed-in customer. Admin endpoints exist (`/api/admin/*`) but there is no admin role.
- Stack & hosting: Node.js 22, single process using `node:http` with no framework and no npm dependencies; static frontend (`demo/flash-sale/shared/public/`). Production: one Node.js process behind a load balancer, hosted Postgres (simulated here by `shared/db.mjs`: per-query network latency, 10-connection pool).
- Environments: only a local instance was available. Live checks were allowed against the local instance only (`PORT=3000 PAYMENT_PORT=4100 node demo/flash-sale/run.mjs naive`). No staging and no production checks.
- Launch: midnight sale (date not given); expected peak 3,000 visitors in 60 s.
- Regulations to keep in mind (flagged, not certified): GDPR / UK GDPR if any EU/UK customers (emails and addresses); CCPA/CPRA for California residents; PCI DSS scope stays small only if card data never touches the app (keep it that way with the provider's hosted fields/checkout); consumer-protection rules on advertised stock ("only 100 pairs").
- Out of scope: the simulated infrastructure itself (`shared/db.mjs`, `shared/fake-payment-provider.mjs`, `shared/seed-data.mjs`); only how the app uses it was reviewed. Fixes (Phase 6): report-only engagement. k6 load tests and Playwright acceptance tests were not re-run here; their existing results are folded into the report.
- **Risk tier: 3 (High)**, because the app takes card payments in-app (server-side charge with an amount the app computes, not a hosted checkout) and holds personal data of public consumers during a time-boxed public drop where an oversell or leak would be very visible. Tier 3 means High findings always block and operational readiness is mandatory. (The verdict would be the same at tier 2: there are open Critical findings.)
