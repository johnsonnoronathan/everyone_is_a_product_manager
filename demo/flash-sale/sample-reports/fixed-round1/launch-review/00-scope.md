# Scope

- **Product:** a one-page flash sale for 100 pairs of limited-edition sneakers ("Limited Edition Holiday Sneakers", $49.99), one pair per customer. The sale opens at midnight with an email blast.
- **Users / scale:** public consumers. Expected 3,000 visitors arriving within 60 seconds of opening (owner's figure). Target used for performance: 3× peak factor (from `demo/flash-sale/peak-brief.json`).
- **Sensitive data:** customer email addresses (identity, order owner) and shipping addresses (`orders.address`). Reviewer first names (public). No passwords. No card data in the app: card payments go through an external provider called server-side.
- **Money flows:** the app server itself calls the provider's charge API (`POST {PAYMENT_URL}/charge`, secret key, idempotency key, 3 s timeout) for the server-side price. This is **not** a hosted checkout: the app owns the amount, idempotency, failure handling and reconciliation. No refunds, coupons or webhooks in the code.
- **Auth & roles:** shopper (signed session token: `payload.HMAC-SHA256` with `TOKEN_SECRET`, 2 h expiry in the demo issuer) and admin (one shared static `X-Admin-Token`). In production a managed identity provider (magic link) issues the session token; `POST /api/login` is a test-only stub behind `DEMO_LOGIN=1` and must be off in production.
- **Stack & hosting:** Node.js 22, no third-party npm dependencies (`node:http`, `node:crypto`, `node:sqlite` for the demo). One Node.js process behind a load balancer today; a second instance may be added later in the season. Hosted Postgres in production; simulated here by `demo/flash-sale/shared/db.mjs` (10-connection pool, ~3 ms per query). Payment provider simulated by `demo/flash-sale/shared/fake-payment-provider.mjs` (Stripe-like, 2% of calls hang for 30 s).
- **Code under review:** `demo/flash-sale/fixed/server.mjs` and the browser front end `demo/flash-sale/shared/public/` (`index.html`, `app.js`, `style.css`). Simulated infrastructure (`shared/db.mjs`, `shared/fake-payment-provider.mjs`, `shared/seed-data.mjs`) is reviewed only for how the app uses it. `demo/flash-sale/run.mjs` is a demo launcher that sets demo-only default secrets.
- **Environments:** only a local instance. No staging or production URL provided. **Live checks allowed against:** a local instance started by the reviewer (`PORT=3100 PAYMENT_PORT=4200 node demo/flash-sale/run.mjs fixed`), nothing else.
- **Launch:** midnight opening (date not given), expected peak 3,000 visitors in 60 s; the whole stock is expected to go in the first minute.
- **Regulations to keep in mind (flagged, not certified):** GDPR / UK GDPR if any customers are in the EU/UK, CCPA/CPRA for California residents (emails and shipping addresses are personal data); PCI DSS scope depends on how the production card integration collects cards (not in the code reviewed); consumer-protection rules on advertised limited stock and start times.
- **Out of scope:** the simulation itself (`db.mjs`, the fake provider, seed data); the demo variant under `demo/flash-sale/naive/`; the production identity-provider and payment integrations (not in the repo); cloud/LB configuration.
- **Risk tier: 3 (High)**, because the app takes card payments in-app: it calls the provider's charge API itself instead of using a hosted checkout, so charge amounts, idempotency, timeouts and reconciliation are this code's responsibility. On top of that, the whole sale happens in a promoted 60-second spike where any failure is public. Tier 3 means: High findings always block, operational readiness is mandatory, and an independent penetration test is recommended before or soon after launch.
